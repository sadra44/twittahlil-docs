# امنیت، احراز هویت پیامکی و کنترل نرخ درخواست‌ها
## Security Architecture, Mobile OTP & Rate Limiting Specifications

این سند استانداردهای امنیتی سامانه، چرخه ورود و صدور توکن‌ها، مکانیزم‌های مقابله با سوءاستفاده‌های سایبری و قوانین کنترل نرخ ترافیک (Rate Limiting) را تشریح می‌کند.

---

## ۱. چرخه حیات احراز هویت پیامکی (SMS OTP Authentication Flow)

ورود به سامانه با شماره تلفن همراه ایران (فرمت `09xxxxxxxxx`) و بدون نیاز به حفظ کلمه عبور پیچیده انجام می‌شود:

```text
[ کاربر ] ──( ۱. شماره موبایل )──► [ سرویس احراز هویت ]
                                          │
                                          ├─ استعلام کش ردیس: آیا کد فعال موجود است؟
                                          │   (محدودیت ارسال مجدد: هر ۶۰ ثانیه حداکثر ۱ پیامک - Cooldown 60s)
                                          │
                                          ├─ تولید کد تصادفی ۶ رقمی امنیتی (CSPRNG)
                                          ├─ ذخیره با انقضای ۱۸۰ ثانیه در دیتابیس و کش: auth:otp:{phone}
                                          │
                                          ▼
                                   [ درگاه پیامک ] ──► ارسال SMS به کاربر
                                          │
[ کاربر ] ◄──( دریافت کد ۶ رقمی )────────┘
   │
   └──( ۲. درج کد در اپلیکیشن )──► [ سرویس احراز هویت ]
                                          │
                                          ├─ مقایسه کد و بررسی سقف خطا (حداکثر ۵ تلاش ناموفق در طول اعتبار کد)
                                          │   (تلاش بیش از ۵ بار = ابطال کد و بلاک ۱۰ دقیقه‌ای)
                                          │
                                          ▼ در صورت تطابق
                                   [ صدور توکن‌های JWT ]
                                   • Access Token (عمر ۱۵ دقیقه - منحصراً در حافظه کلاینت / React State)
                                   • Refresh Token (عمر ۳۰ روز در کوکی HttpOnly)
```

## ۲. مشخصات توکن‌های دسترسی و ذخیره‌سازی امن (JWT Token Specifications & Storage Security)

* **Access Token (توکن دسترسی کوتاه‌مدت):**
  * در قالب هدر استاندارد `Authorization: Bearer <TOKEN>` ارسال می‌شود.
  * **الزام امنیتی ذخیره‌سازی کلاینت:** برای پیشگیری کامل از سرقت توکن از طریق آسیب‌پذیری‌های XSS، Access Token هرگز نباید در `localStorage` یا `sessionStorage` ذخیره گردد. این توکن منحصراً در حافظه موقت اپلیکیشن (Application Memory نظیر React Context یا Zustand Store) نگهداری می‌شود و در صورت رفرش صفحه از طریق رفرش توکن کوکی بازیابی می‌گردد.
  * ساختار پی‌لود (Payload):
    ```json
    {
      "sub": "c1f7b820-22e3-4f9e-a89b-944a956d2994",
      "handle": "dr_sohrabi",
      "tier": "VERIFIED_ANALYST",
      "is_verified": true,
      "iat": 1728470000,
      "exp": 1728470900
    }
    ```
* **Refresh Token (توکن نوسازی بلندمدت):**
  * منحصراً در کوکی امن با ویژگی‌های `HttpOnly`, `SameSite=Strict`, `Secure` ذخیره می‌شود و جاوااسکریپت کلاینت هیچ دسترسی به آن ندارد.
  * نسخه هش‌شده توکن در جدول پایگاه داده نگهداری می‌شود تا با خروج کاربر (Logout) یا مسدودسازی، بلافاصله از تمامی دستگاه‌ها نامعتبر گردد.

## ۳. جدول قوانین جامع کنترل نرخ (Rate Limiting Rules)

برای مقابله با حملات نفی سرویس (DDoS)، بات‌های اسپمر و ثبت‌نام انبوه، قوانین زیر در لایه معکوس پروکسی (Nginx/Gateway) و با حافظه ردیس با الگوریتم پنجره کشویی (Sliding Window) اعمال می‌شود:

| قلمرو / عملیات | کلید رهگیری (Tracking Key) | سقف مجاز | پنجره زمانی | رفتار در صورت نقض قانون |
| :--- | :--- | :---: | :---: | :--- |
| **درخواست ارسال مجدد پیامک OTP** | شماره تلفن همراه | ۱ بار | ۶۰ ثانیه | خطای ۴۲۹ با نمایش ثانیه‌شمار معکوس ۶۰ ثانیه‌ای |
| **درخواست پیامک OTP** | آدرس IP کاربر | ۵ بار | ۱ ساعت | خطای ۴۲۹ و مسدودسازی موقت IP |
| **بررسی کد OTP** | شماره تلفن همراه | ۵ بار | ۱۸۰ ثانیه | ابطال کد و قفل شماره به مدت ۱۰ دقیقه |
| **انتشار توییت (عادی)** | شناسه کاربر (`user_id`) | ۱۰ توییت | ۱ ساعت | خطای ۴۲۹ با پیام: «سقف مجاز توییت ساعتی» |
| **انتشار توییت (تحلیل‌گر)**| شناسه کاربر (`user_id`) | ۳۰ توییت | ۱ ساعت | خطای ۴۲۹ |
| **انتشار نظر و پاسخ** | شناسه کاربر (`user_id`) | ۳۰ نظر | ۱ ساعت | خطای ۴۲۹ |
| **پسندیدن توییت (Like)**| شناسه کاربر (`user_id`) | ۱۲۰ لایک | ۱ ساعت | نادیده گرفتن درخواست‌های اضافی (Debounce در کلاینت ۳۰۰ms) |
| **درخواست آپلود مدیا (Presigned URL)** | شناسه کاربر (`user_id`) | ۲۰ درخواست | ۱ ساعت | خطای ۴۲۹ با پیام: سقف آپلود موقت تکمیل شد |
| **کوئری‌های عمومی API** | آدرس IP مشترک | ۳۰۰ درخواست | ۱ دقیقه | خطای ۴۲۹ (مسدودسازی ۵ دقیقه‌ای IP) |

## ۴. اقدامات ضدآسیب‌پذیری (Application Security Hardening)

1. **لایه پاکسازی XSS در بک‌اند (Backend XSS Sanitization Layer):**
   * تمامی متون ارسالی کاربران (متن توییت، بایوگرافی، کامنت‌ها) باید پیش از درج در پایگاه داده MySQL / MariaDB، در سمت سرور توسط کتابخانه پاکسازی معتبر (مانند DOMPurify یا sanitize-html) پردازش و خنثی‌سازی شوند. تکیه بر اعتبارسنجی کلاینت اکیداً ممنوع است.
2. **مهار ترافیک لایک خوش‌بینانه (Client-Side Debouncing & Throttling):**
   * برای جلوگیری از اسپم سرور توسط کلیک‌های متوالی روی دکمه لایک، رابط کاربری با رویکرد Optimistic UI بلافاصله وضعیت آیکون را تغییر می‌دهد؛ اما درخواست شبکه را با یک دی‌بانس (Debounce) ۳۰۰ میلی‌ثانیه‌ای یا تراتل ارسال می‌کند تا تنها آخرین وضعیت کاربر به سرور مخابره شود.
3. **سیاست امنیت محتوا (Content Security Policy - CSP):**
   * اعمال هدرهای امنیتی سخت‌گیرانه برای جلوگیری از بارگذاری اسکریپت‌های ناشناس خارج از دامنه‌های پلتفرم.
4. **رمزنگاری در حال انتقال و سکون (Encryption in Transit & at Rest):**
   * اجبار پروتکل HTTPS (TLS 1.3) و فعال‌سازی HSTS با عمر ۱ ساله.
   * رمزنگاری داده‌های حساس اسناد هویتی تحلیل‌گران در فضای ذخیره‌سازی ابری با الگوریتم AES-256.
